## 🔴 问题 1: StealthGcm 填充/解填充结构不匹配

### 问题描述
`StealthGcm.java` 中的 `addRandomPadding` 和 `removeRandomPadding` 方法逻辑不一致，导致解密必定失败。

**addRandomPadding (修复前)**:
```
结构: [prefixLen 字节随机][4 字节 realLen 大端][realLen 字节真实数据][suffixLen 字节随机]
长度标记位置: prefixLen 偏移处（随机位置，8-39 之间）
```

**removeRandomPadding (修复前)**:
```java
int prefixLen = this.random.nextInt(32) + 8;  // 生成新随机数，完全无用
int realLen = 从末尾 4 字节读取;  // 读取位置完全错误（应从 prefixLen 偏移读取）
System.arraycopy(padded, len - 4 - realLen, data, 0, realLen);  // 复制位置也错
```

**问题根因**:
1. encode 把长度标记写在随机 `prefixLen` 偏移处
2. decode 却从末尾 4 字节读长度（位置完全不对）
3. decode 中 `random.nextInt(32)+8` 生成新随机数，实际未使用

### 修复方案
重新设计填充结构，将长度标记固定到数据开头（无随机前缀）：

**新结构**:
```
[4 字节 realLen 大端][realLen 字节真实数据][suffixLen 字节随机后缀]
```

**addRandomPadding (修复后)**:
```java
private byte[] addRandomPadding(byte[] data) {
    int suffixLen = this.random.nextInt(32) + 8;  // 8-39 字节后缀
    int realLen = data.length;
    byte[] padded = new byte[4 + realLen + suffixLen];

    // 头部: 4 字节真实数据长度（大端）
    padded[0] = (byte)(realLen >> 24);
    padded[1] = (byte)(realLen >> 16);
    padded[2] = (byte)(realLen >> 8);
    padded[3] = (byte)realLen;

    // 真实数据
    System.arraycopy(data, 0, padded, 4, realLen);

    // 后缀: 随机数据
    byte[] suffix = new byte[suffixLen];
    this.random.nextBytes(suffix);
    System.arraycopy(suffix, 0, padded, 4 + realLen, suffixLen);

    return padded;
}
```

**removeRandomPadding (修复后)**:
```java
private byte[] removeRandomPadding(byte[] padded) {
    // 从固定位置读取真实数据长度
    int realLen = ((padded[0] & 0xFF) << 24) |
                  ((padded[1] & 0xFF) << 16) |
                  ((padded[2] & 0xFF) << 8) |
                  (padded[3] & 0xFF);

    byte[] data = new byte[realLen];
    System.arraycopy(padded, 4, data, 0, realLen);
    return data;
}
```

**修复理由**: 长度标记在固定位置（offset=0），decode 不需要知道 prefixLen，彻底消除随机位置问题。仅客户端代码变更，不影响服务端 shell 模板（服务端 shell 只做 AES-GCM 解密 + Base64，不涉及填充逻辑）。

### 涉及文件
- `src/main/java/shells/cryptions/Stealth/StealthGcm.java`

## 🟡 问题 2: key.getBytes() 使用平台默认编码

### 问题描述
所有 Java 系列加密器直接使用 `key.getBytes()`，依赖 JVM 默认 `file.encoding`。在不同操作系统或不同启动参数下，`file.encoding` 可能是 GBK、UTF-8、ISO-8859-1 等，导致同一密钥在不同平台派生出不同的字节数组，密钥不一致。

**受影响的调用点**:
```java
new SecretKeySpec(this.key.getBytes(), "AES")  // 平台依赖
```

### 修复方案
将所有 `key.getBytes()` 替换为 `key.getBytes(StandardCharsets.UTF_8)`，统一使用 UTF-8 编码。

### 涉及文件（6 个 Java 系列加密器）

| 文件 | 修复处数 | 导入 |
|------|---------|------|
| `shells/cryptions/Stealth/StealthGcm.java` | 2 处 | `java.nio.charset.StandardCharsets` |
| `shells/cryptions/JavaAesGcm/JavaAesGcm.java` | 2 处 | `java.nio.charset.StandardCharsets` |
| `shells/cryptions/JavaAes/JavaAesRaw.java` | 2 处 | `java.nio.charset.StandardCharsets` |
| `shells/cryptions/JavaAes/JavaAesBase64.java` | 2 处 | `java.nio.charset.StandardCharsets` |
| `shells/cryptions/JavaAes/JavaAesBase64Ex.java` | 2 处 | `java.nio.charset.StandardCharsets` |
| `shells/cryptions/JavaAes/JavaAesWeblogic.java` | 2 处 | `java.nio.charset.StandardCharsets` |

### 未修改的加密器
- **cshapAes 系列**（cshapAesBase64、cshapAesRaw）：key 同时用作 IV，且 C# 服务端编码可能不同，改动风险较高，本次不修改。

### 修复示例
```java
// 修复前
SecretKeySpec keySpec = new SecretKeySpec(this.key.getBytes(), "AES");

// 修复后
SecretKeySpec keySpec = new SecretKeySpec(this.key.getBytes(StandardCharsets.UTF_8), "AES");
```

## 🟡 问题 3: PBKDF2 使用固定盐

### 问题描述
`functions.deriveKeyPBKDF2(String password)` 使用硬编码盐值 `GodzillaX_Salt_2024`，源码注释承认实际应使用随机盐，但当前无会话级盐值存储机制。

**风险**:
- 固定盐意味着所有用户使用相同盐派生密钥
- 攻击者只需为该固定盐预计算彩虹表，即可破解所有使用该盐派生的密钥
- 不符合 PBKDF2 的安全最佳实践（每个会话应有独立随机盐）

### 约束分析
- `generate()` 方法生成 shell 文件时必须用固定盐（因为服务端 shell 代码中硬编码了固定盐）
- `getSecretKeyX()` 如果改用随机盐，会导致客户端密钥与服务端不匹配
- 旧 shell 数据库中没有 salt 字段，不能破坏现有 shell 可用性

### 修复方案（基础设施 + 向后兼容）

**阶段 1（本次完成）: 添加随机盐基础设施**

1. **`util/functions.java` 新增方法**:
   ```java
   // 生成指定长度的随机盐
   public static byte[] generateRandomSalt(int length) {
       byte[] salt = new byte[length];
       SecureRandom sr = new SecureRandom();
       sr.nextBytes(salt);
       return salt;
   }

   // 生成默认 16 字节随机盐
   public static byte[] generateRandomSalt() {
       return generateRandomSalt(16);
   }
   ```

2. **`core/Db.java` 新增 shell 级 KV 读写方法**:
   ```java
   // 读取 shell 级配置
   public static String getShellEnv(String shellId, String key)

   // 写入 shell 级配置（不存在则新增，存在则更新）
   public static synchronized boolean setShellEnv(String shellId, String key, String value)
   ```
   利用已有的 `shellEnv` 表（`shellId | key | value`），新增约定键 `ENV_PBKDF2_SALT`。

3. **`core/shell/ShellEntity.java` 新增方法**:
   ```java
   // 获取或创建该 Shell 的 PBKDF2 随机盐
   // 首次调用生成 16 字节随机盐并存入 shellEnv，后续从 shellEnv 读取
   public String getOrCreateSalt()

   // 使用随机盐派生密钥（未来 shell 模板支持随机盐后启用）
   public String getSecretKeyXWithSalt()
   ```

4. **`getSecretKeyX()` 保持固定盐兼容**:
   ```java
   public String getSecretKeyX() {
       // 为保持与 generate() 时生成的 shell 文件兼容，仍使用固定盐
       byte[] derivedKey = functions.deriveKeyPBKDF2(this.getSecretKey());
       // ...
   }
   ```

**阶段 2（未来）: 启用随机盐**
- 修改 shell 模板（.bin 二进制文件），在服务端代码中支持从请求中获取盐值
- `getSecretKeyX()` 切换为 `getSecretKeyXWithSalt()`
- 新生成的 shell 自动使用随机盐，旧 shell 降级到固定盐

### 向后兼容性
- ✅ 旧 shell 数据库无 salt 字段，`getSecretKeyX()` 仍用固定盐，完全兼容
- ✅ 新增方法不影响现有功能
- ✅ 首次调用 `getOrCreateSalt()` 时自动生成并保存随机盐，不影响旧 shell

### 涉及文件
- `src/main/java/util/functions.java` — 新增 `generateRandomSalt()`
- `src/main/java/core/Db.java` — 新增 `getShellEnv()` / `setShellEnv()`
- `src/main/java/core/shell/ShellEntity.java` — 新增 `getOrCreateSalt()` / `getSecretKeyXWithSalt()`

## 🟡 问题 4: Http 静态块全局 SSL 污染

### 问题描述
`Http.java` 在类加载时通过静态块调用 `trustAllHttpsCertificates()`，该方法修改全局 `HttpsURLConnection.setDefaultSSLSocketFactory()`，影响同一 JVM 中所有使用 HTTPS 的组件。

**修复前代码**:
```java
public class Http {
    static {
        trustAllHttpsCertificates();  // 类加载时修改全局 SSL
    }

    private static void trustAllHttpsCertificates() {
        // ...
        HttpsURLConnection.setDefaultSSLSocketFactory(sc.getSocketFactory());
        // ↑ 修改全局默认，影响同 JVM 所有组件
    }
}
```

**风险**:
- GodzillaX 作为开发工具，用户可能在同一 JVM 中运行其他需要严格 SSL 验证的组件
- 全局信任所有证书会让这些组件也失去 SSL 保护
- 违反最小权限原则

### 修复方案

**1. 删除静态块**:
```java
// 静态块已删除：不再在类加载时修改全局 SSLSocketFactory
// 改为在 SendHttpConn 中对每个 HttpsURLConnection 实例单独 setSSLSocketFactory
```

**2. 新增 `createTrustAllSSLContext()` 静态方法**:
```java
private static SSLContext createTrustAllSSLContext() {
    try {
        TrustManager[] trustAllCerts = new TrustManager[]{new miTM()};
        SSLContext sc = SSLContext.getInstance("TLS");
        sc.init((KeyManager[])null, trustAllCerts, new SecureRandom());
        return sc;  // 返回 SSLContext，不修改全局
    } catch (Exception var2) {
        var2.printStackTrace();
        return null;
    }
}
```

**3. 新增 `getTrustAllSSLContext()` 实例方法（懒加载 + 缓存）**:
```java
private SSLContext getTrustAllSSLContext() {
    if (this.trustAllSSLContext == null) {
        this.trustAllSSLContext = createTrustAllSSLContext();
    }
    return this.trustAllSSLContext;
}
```

**4. 在 `SendHttpConn` 中实例级设置**:
```java
if (httpConn instanceof HttpsURLConnection) {
    HttpsURLConnection httpsConn = (HttpsURLConnection)httpConn;
    httpsConn.setHostnameVerifier(hostnameVerifier);
    // 实例级 SSL：只对该连接生效，不污染全局默认 SSLSocketFactory
    SSLContext ctx = getTrustAllSSLContext();
    if (ctx != null) {
        httpsConn.setSSLSocketFactory(ctx.getSocketFactory());
    }
}
```

**5. 新增实例字段缓存**:
```java
private SSLContext trustAllSSLContext;
```

### 修复效果
- ✅ 不再修改全局 `HttpsURLConnection.setDefaultSSLSocketFactory`
- ✅ 仅对 GodzillaX 自身的 HTTPS 连接信任所有证书
- ✅ 同 JVM 其他组件的 SSL 验证不受影响
- ✅ SSLContext 每实例创建一次并缓存，性能无影响

### 涉及文件
- `src/main/java/util/http/Http.java`

## 🟢 问题 5: 资源目录冗余

### 问题描述
`src/main/java/shells/cryptions/Stealth/template/` 和 `src/main/resources/shells/cryptions/Stealth/` 存在完全相同的 4 个模板文件，`Generate.java` 只读 resources 路径，java 路径下的 template 目录冗余。

**冗余文件**:
```
src/main/java/shells/cryptions/Stealth/template/
├── rawCode.bin
├── rawGlobalCode.bin
├── shell.jsp
└── shell.jspx
```

**Generate.java 实际加载路径**:
```java
Generate.class.getResourceAsStream("/shells/cryptions/Stealth/rawCode.bin")
// ↑ classpath 路径，对应 src/main/resources/shells/cryptions/Stealth/
```

### 修复方案
直接删除 `src/main/java/shells/cryptions/Stealth/template/` 目录及其下 4 个文件。

### 删除文件清单
- `src/main/java/shells/cryptions/Stealth/template/rawCode.bin` ✅ 已删除

- `src/main/java/shells/cryptions/Stealth/template/shell.jsp` ✅ 已删除
- `src/main/java/shells/cryptions/Stealth/template/shell.jspx` ✅ 已删除
- `src/main/java/shells/cryptions/Stealth/template/` 目录 ✅ 已删除

### 修复效果
- ✅ 消除冗余资源，项目结构更清晰
- ✅ Maven 打包时 resources 目录才是资源来源，删除不影响编译
- ✅ 避免维护两份相同文件导致的不一致风险
